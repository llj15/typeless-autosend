# Leave-to-send implementation notes

The requested behavior is specified in [design-leave-to-send.md](design-leave-to-send.md). These notes describe delivery decisions, content alignment and the unit-test verification boundary.

## Delivery on departure

Focus notifications for a change to another window or input in the original application request immediate delivery to the captured PID. Application deactivation takes the same path. During the 150 ms paste buffer, those departures are retained until settlement reads the captured original input and establishes its baseline. Intercepted outside clicks use the ordered tap path described below.

Departure checks the captured original input object for a confirmed protected-content or caret change; it does not compare the newly focused input against the old baseline. Unknown focus identity or unreadable text alone is not proof of editing. Confirmed editing, a newer local record, missing permissions, Secure Input and process exit still prevent delivery.

Caret and selection comparisons require confirmation that the original input remains focused. A control may clear its Accessibility selection when it blurs; that reset alone does not prove a user edit. A confirmed departure notification is retained through settlement and takes precedence over a cached focused-element identity. Protected-content checks still use the original input during departure. Cancellation diagnostics distinguish content, caret and selection changes and identify the original application without logging input text.

The first cancellation reason is stored with its attempt before asynchronous reporting. Polling and the pending-state consumer use that same reason, and consuming an outcome atomically returns either its sent destination or its cancellation cause. A deferred callback cannot replace the cause with a generic inactive-attempt error or report against a newer epoch.

Within the same window, a focused child or non-window ancestor proven to belong to the original input keeps the countdown. A relationship that cannot be determined also waits for later observations or expiry. A confirmed different window requests delivery independently of input ancestry. Focus and deactivation notifications that arrive while the state lock is busy are retained; delivery waits for queued notifications, and capture generations and attempt epochs keep old events from affecting new work.

For a confirmed outside click, Return is inserted with the current callback's `tapPostEvent` proxy before that callback returns the click. Apple documents this ordering in [CGEvent.tapPostEvent](https://developer.apple.com/documentation/coregraphics/cgevent/tappostevent%28_%3A%29). Posting to the PID and then returning the mouse event uses two different insertion points and does not establish that ordering.

When a click is captured before settlement, it and subsequent key, button, drag and scroll events are copied and held for at most one second, with a 256-event limit. Successful settlement uses a marked null event to request a new callback, whose current proxy inserts Return before returning the saved mouse-down. The proxy is never retained across callbacks. The remaining gesture and queued input follow the returned mouse-down. Cancellation, timeout or a failed carrier releases input without Return and prevents a late completion from submitting the abandoned click.

The first mouse-down also needs protection when another thread is inspecting the input. Previously that callback passed the click through and marked the attempt interrupted when it could not acquire the state lock; later validation reported a generic cancellation. A pending click classification now holds the copied event and following input in the bounded gate while inspection becomes available. Holding an unclassified click does not prove departure: only a confirmed outside result requests pre-click Return. An inside, unknown or other-application result releases the input under the existing policy. Classification and replay remain bound to the original gate serial and attempt ownership so a late result cannot submit a newer dictation. The final queue decision and Return posting share the gate lock, closing a late-arriving click's release window; AX reads and send authorization stay outside that lock. Native posting latency while holding it has not been measured.

Click diagnostics record classification, contention and release decisions with attempt ownership, without input contents or screen coordinates. They are written asynchronously with their observation time, avoiding stdout work in the event callback. These records distinguish a click that was deliberately passed through from one held for ordered delivery; a delivery record still does not acknowledge submission by the target application. Each native classification also records the hit element's role, the number of AX reads, and the hit-test and total time in milliseconds. An inconclusive ancestry walk adds a `cause` (`deadline`, `ax_timeout`, `element_invalid`, `unreadable`, `depth`, `cycle` or `application_hit`), how far each side climbed and where it stopped, and the first failed read. Diagnostics leave the AX reads unchanged, so the recorded times match classification without them.

Click replay rechecks attempt ownership, health and the captured original content. While the original application is frontmost, a focus change away from the original input ends the attempt rather than requesting delivery: once focus has changed, a Return posted to the PID reaches the new target. Countdown expiry rechecks that the frontmost application still focuses the original input, covering a move whose notification has not been handled. A confirmed edit of the protected region remains the reported reason when present. After deactivation, delivery uses the saved PID, whose application keeps its focused input in the background. The PID route also has no strict ordering guarantee relative to a released mouse event. An unreadable identity remains unknown and retains the existing design's send policy. A replayed Typeless paste samples the reported focus immediately before it is released; the unit tests do not establish when a real application's AX focus reflects the preceding replayed click.

The two ancestry walks advance together. Separate input branches joining at a known common ancestor establish an outside relationship even when ancestors above it cannot be read. Each walk may climb 100 levels: a web-based composer was measured 33 levels below its window, so the former 24-level limit left clicks that only meet at the window inconclusive. The 25 ms AX deadline, not the level limit, bounds how long a click is held; each step compares only its new nodes against the other path. Without that evidence or completed boundary walks, the relationship remains unknown. A blank-area click whose target cannot be distinguished from the original input therefore waits for another confirmed departure or expiry.

Other departures and expiry keep `CGEvent.postToPid`. A PID identifies an application, not a terminal pane or first responder; that path cannot by itself select the original input after focus has changed. The unit tests establish routing decisions and callback order with injected posting functions. They do not establish native carrier delivery, the receiving control, or event processing by a real application. The null carrier has no click or key action, and failure to receive its callback must release the held input without sending. AppKit describes ordinary keyboard dispatch in [Apple's Handling Key Events guide](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/HandlingKeyEvents/HandlingKeyEvents.html). No input refocusing or element-level submission action is introduced.

Expiry relies on the latest foreground observations and notifications, then checks health and authorization without another AX read. A focus or content change whose notification has not yet arrived can fall between the last observation and actual event delivery. Native application processing order remains outside the unit-test evidence.

## Paste association and content alignment

Each captured paste is consumed once and associated with a local database record. A paste observed while the newest local record is incomplete cannot establish that association; the implementation waits for a matching capture and eventually skips a stale completion. This prevents a delayed paste from an older dictation from being assigned to a newly started recording. No clipboard text is read.

After the initial 150 ms buffer, an empty or unchanged value can still be a cached pre-paste snapshot. A changed value without the pasted text can also be an unrelated output refresh. Settlement retries the saved original input every 50 ms, for at most one second after arming, retaining any departure request; the delivery timer waits for settlement. Minimum paste evidence requires the complete text, allowing CRLF/LF equivalence and omission of a single final newline. Matching historical text alone cannot establish the insertion location; region alignment or the whole-input fallback still applies. If the window expires without observing a paste, the attempt skips unless a reported selection proves an identical-text replacement. A capture event alone does not prove that the application accepted the paste. This avoids submitting an empty input or a pre-existing draft after an ineffective paste. Replacing a reported selection with the same nonempty text remains supported; without selection information, an unchanged value cannot establish that replacement.

Content alignment protects the pasted lines and accepts refreshes elsewhere. Ambiguous alignment, an unknown selection replacement that cannot be recovered, or an alignment larger than the configured bounds uses the whole input as a baseline. These cases may cancel on unrelated refreshes. When the text changes, settlement locates the paste from the before/after texts. An input may report caret offsets that omit characters its AX value contains, so the changed-text path does not use a reported caret as a text position or compare it with text length. Unchanged text is a special case: it requires a valid selected range whose exact text equals the paste, followed by a collapsed selection at the expected end. That verified selected range identifies the protected occurrence; unreliable offsets conservatively leave settlement pending. When the after text is exactly the before text with one range replaced by the paste, that range is the insertion; otherwise content alignment applies, and an unresolvable snapshot still uses the documented whole-input fallback. A buffer edit is cancelled when the snapshots establish that the protected content changed. The caret read at settlement becomes the baseline, and only later caret readings are compared with it, so caret movement within the paste buffer itself is not detected.

## Verification boundary

Development used failing unit cases followed by implementation and passing cases. The independent review agents use GPT-6 Solar (`gpt-6-sol`) with `max` reasoning and receive no inherited conversation history.

Tests compile separate executables and use pure algorithms, simulated events, temporary SQLite databases, and stubbed system APIs or commands. No real application integration or end-to-end tests were run. These checks do not move desktop focus, type, click, or submit content. Local installation and service health checks are separate operations performed only when requested.
