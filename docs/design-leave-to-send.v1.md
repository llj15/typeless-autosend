# 改造方案：离开即发送

基线：`main` @ `5a2f77c`（PR #6 focus-aware-autosend 合并后）
分支：`feature/leave-to-send`
日期：2026-10-23

## 核心思想

只有用户改了刚转写的那段文字才取消；用户一离开原输入框就立即发送；一直停在原输入框里不动，才等满倒计时。

现在 `main` 的思路是"无法确认安全就不发"：按键、屏幕刷新、切走、到点时读不到输入框，都会取消，导致大多数正常场景发不出去。本方案改为"只有确认用户改过才不发"。

## 三条原则

1. **判据只看内容**：原文所在区域的文字或光标变了，才算改过。按键、点击、切换应用本身都不算。
2. **离开即发送**：同应用里点别处、换窗口、切到别的应用或桌面，立即发回车。
3. **到点不再复查**：倒计时期间一直在实时监听，到点时没被中断就直接发。

代码中不出现任何具体应用名称或按键键位。

## 流程

```
① 触发
   数据库出现一条 completed 的新转写
   → 记下原应用 PID、输入框对象、转写原文
   → 在输入框内容里找到包含原文的行，作为"基准区域"；记下光标位置
   → 等 150ms 粘贴缓冲结束后锁定基准

② 中断（永久取消，不发送）
   a. 基准区域的文字变了
   b. 光标位置变了（应用不报告光标时，此项自然不触发）
   c. 输入框内容里找不到原文了
   d. 数据库出现一条更新的记录（新一轮听写开始，不论状态）
   e. 原应用退出 / 权限丢失 / 进入 Secure Input
   a、b、c 只在原应用在前台时检查

③ 立即发送（离开原输入框）
   a. 同应用内点原输入框以外的地方（消息区、空白、其他分屏、其他控件）
      → 拦住点击 → 先发回车 → 再放行点击
   b. 同应用切到另一个窗口
      → 立即发回车
   c. 原应用失去前台（点别的应用、Dock、触控板手势、任何快捷键）
      → 立即后台按进程发回车
   离开发生在 150ms 缓冲内的，等缓冲结束、确认原文在框里后再发

④ 不处理（倒计时继续）
   · 按键事件本身（是否改了内容由 ②a、②b 判定）
   · 点原输入框里面但光标没动

⑤ 到点
   一直停在原输入框里没动 → 发回车
```

## 与当前 main 的行为差异

| 场景 | 当前 main | 本方案 |
|---|---|---|
| 判断"原框被改过" | 任意按键即算；整个输入框的值变化即算 | 只看原文所在区域的文字和光标 |
| 输入框的值包含整屏内容（如终端） | 屏幕刷新被误判为编辑，取消 | 只看基准区域，其他区域刷新不影响 |
| 新一轮听写 | 只识别 Fn 键 | 数据库出现新记录即算，与快捷键无关 |
| 同应用点消息区、空白处 | 取消 | 先回车，再放行点击 |
| 同应用点另一个分屏 | 取消（控件不报告 AXEnabled） | 先回车，再放行点击 |
| 点原输入框里面、光标没动 | 取消 | 不处理 |
| 点别的应用、AX 命中测试失败 | 取消（`cannot classify mouse target`） | 原应用失去前台，立即发送 |
| 切到别的应用或桌面 | 倒计时继续；到点重读输入框，常因读不到或内容变化而放弃 | 立即后台发送 |
| 到点 | 重读输入框比对文字和选区 | 只确认未中断、PID 存活 |
| 发送方式 | `postToPid` | 不变 |

## 代码改动

| 位置 | 当前 | 改为 |
|---|---|---|
| `InputMonitor.handle` 键盘分支 | 前台任意按键即取消；Tab、Cmd+Tab 特判 | 删除，按键不再作为判据 |
| `InputMonitor.handle` Fn 判断 | Fn 即取消 | 删除；改为 `main.swift` 轮询数据库时发现更新的记录即中断 |
| `InputMonitor.handle` 鼠标分支 | 先做 AX 命中测试，失败即取消 | 只处理原应用在前台时的点击；点的不是原输入框（也不是其祖先或子元素）→ 先回车再放行 |
| `mouseDecision` / `separateEditableTarget` | 要求 AXEnabled、可聚焦、角色为文本框 | 简化为"是否原输入框"判断 |
| AX 内容/选区变化通知 | 整个输入框的值变化即取消 | 只比对基准区域和光标 |
| `handleFocusNotification` | 焦点变化或读不到即取消 | 同应用换窗口 → 立即发送；原应用在后台时忽略 |
| 新增：原应用失去前台 | 无 | 监听 `NSWorkspace.didDeactivateApplicationNotification`，命中原 PID → 立即 `postToPid` |
| `deliver`（到点） | `validateAttempt` 重读比对 | 只确认未中断、PID 存活，然后发回车 |

不变：数据库触发、150ms 粘贴缓冲、`postToPid` 发送方式、暂停和恢复、权限与 Secure Input 检查。

## 已验证的前提（2026-10-22 实测）

| 前提 | 结果 | 说明 |
|---|---|---|
| 后台按进程发回车，终端类应用 | ✅ | 应用在后台，回车后命令执行 |
| 后台按进程发回车，Chromium 内核应用 | ✅ | 回车能触发提交；普通字符在后台不会插入 |
| 听写开始时数据库立即写入记录 | ✅ | 开口约 0.1 秒内插入，`status` 为空，完成后变为 `completed` |
| 切换应用或桌面时能收到"失去前台"通知 | ✅ | 触控板四指切桌面时收到 `DEACTIVATED` |
| 输入框的值包含整屏内容 | ✅ 已确认 | 终端类应用暴露单个 `AXTextArea`，值为整屏文字，空闲时也在变化，选区恒为 `0,0` |
| 在整屏内容中只比对原文所在行 | 未验证 | 需在实现后实测 |

注意：用临时编译的测试程序发送按键时，必须单独授予辅助功能权限，并通过 `launchctl submit` 以独立进程启动；从终端直接启动时，即使系统接口报告有权限，事件仍可能被丢弃。重新编译会使授权失效。

## 风险

1. **基准区域定位**：原文在屏幕上重复出现，或被折行、截断，可能找错或找不到。找不到时按 ②c 取消，宁可不发也不误发。
2. **后台投递依赖应用实现**：已实测的两类应用都能接受后台回车，但不保证所有应用都能。
3. **离开即发送的副作用**：手势切桌面开始后又中途取消，回车可能已经发出。
4. **重新授权**：重新编译后需重新授予辅助功能权限。

## 测试

单元测试（`tests/test_runtime.py`）：每条规则至少一个用例。

| 规则 | 用例 |
|---|---|
| ②a | 基准区域文字变化 → 取消 |
| ②a 反例 | 基准区域以外的内容变化 → 不取消 |
| ②b | 光标位置变化 → 取消 |
| ②c | 内容中找不到原文 → 取消 |
| ②d | 数据库出现更新的记录 → 取消 |
| ③a | 同应用点原框以外 → 先发送，再放行点击 |
| ③b | 同应用切换窗口 → 立即发送 |
| ③c | 原应用失去前台 → 立即后台发送 |
| ③ 缓冲 | 150ms 缓冲内离开 → 缓冲结束后发送 |
| ④ | 按键但内容不变 → 不取消；点原框且光标不动 → 不取消 |
| ⑤ | 停留不动 → 到点发送 |
